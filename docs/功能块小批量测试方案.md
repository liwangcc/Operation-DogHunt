# 功能块小批量测试方案 v0.1

状态：方案待确认，尚未开发。日期：2026-11-11（北京时间）。

## 1. 目标与边界

- 验证这套流程能不能跑通：每个影响因素做一个功能块，每块有独立提示词，单独调用一次模型给出本块结论，再由汇总块合成最终判断。
- 比较结论的三种表达方式：只给方向、方向加把握、方向加把握加影响分值。看哪一种对汇总更有用。
- 范围：NBA 赛前全场让分和全场大小分。不含亚洲盘、半场、单节和球员单项数据。
- 小批量测试能回答什么、不能回答什么，见第 7 节。

## 2. 第一批范围（推荐）

| 功能块 | 角色 | 主要影响 | 为什么放第一批 |
| --- | --- | --- | --- |
| 球队实力（含主场） | 给出基准分差 | 让分 | 让分判断的主线，用比分就能算 Elo |
| 节奏与得分环境 | 给出基准总分 | 大小分 | 大小分判断的主线 |
| 赛程与体能 | 修正分差和总分 | 两者 | 数据最容易得到，只靠赛程就能算 |
| 汇总 | 合成最终判断 | 两者 | 测试三种表达方式 |

- **三块用同一类数据**：赛程、比分和球队技术统计，接一个数据源就够。
- **主场优势并入球队实力块**：Elo 本身就含主场修正，单独成块会重复计算。
- **市场盘口不单独成块投票**：盘口只给汇总块，用来做对照和判断。三个因素块都**不看盘口**，避免模型被盘口带着走。
- **伤病第二批首选**：伤病影响很大，但需要伤病数据源，还要把缺阵换算成分数，第一批先不做。

## 3. 一场比赛的流程

```text
选场：从已保存的盘口快照中选 N 场未开赛比赛
→ 程序计算三块指标，固定成本场的“数据快照”
→ 三个因素块各调用一次模型（各用自己的提示词，不看盘口，不看其他块的结论）
→ 汇总块按 S-A / S-B / S-C 三个版本各调用一次（看各块结论和盘口）
→ 程序基线 P0 同时给出结论（不调用模型）
→ 开赛前补取收盘盘口 → 赛后取比分 → 程序结算 → 人工复盘
```

## 4. 各块的输入和输出

### 4.1 因素块的统一输出格式

每个因素块都要求模型返回同样字段的 JSON，再由程序写进 CSV：

```json
{
  "block": "strength",
  "prompt_version": "strength_v1",
  "spread_lean": "home | away | neutral | insufficient",
  "spread_confidence": 0,
  "margin_pts": 0.0,
  "total_lean": "high | low | neutral | insufficient",
  "total_confidence": 0,
  "total_pts": 0.0,
  "reasons": ["每条依据都要引用输入里的具体指标，最多 3 条"],
  "missing": ["缺少的数据"]
}
```

- `spread_lean`：本块认为利好主队还是客队。`total_lean`：本块认为总分会偏高还是偏低。因素块不看盘口，所以这里判断的是因素本身的方向，**不是买大还是买小**。
- `confidence`：0–100，表示模型对这个方向判断的把握。**不是赢盘概率**。
- `margin_pts`：本块认为的主队净胜分，正数表示主队占优。`total_pts`：本块认为的总分。两个值是“基准值”还是“修正值”，见 4.2 的“角色”列，由程序固定，不让模型自己决定。
- 某个方向与本块无关时，填 `neutral`，分值填 0。比如节奏块的让分方向通常为 `neutral`。
- 提示词统一要求：只用输入里给的数据；不得引用输入以外的伤病、新闻或赛果；数据不足时填 `insufficient`，不要硬猜。

### 4.2 三个因素块

| 功能块 | 分值角色 | 程序先算好的指标（输入） | 模型要判断什么 |
| --- | --- | --- | --- |
| 球队实力 | `margin_pts` 为基准分差 | 双方 Elo 和 Elo 推算的分差（含主场）；赛季与近 10 场的净效率（每 100 回合净胜分）；主客场战绩；本季已赛场次 | 这个基准分差可不可信，要不要调整；季初样本少时把握要降低 |
| 节奏与得分环境 | `total_pts` 为基准总分 | 双方赛季与近 10 场的回合数、进攻效率、防守效率；联盟平均；公式推算的总分（预计回合数 × 预计每回合得分） | 推算总分可不可信，偏高还是偏低 |
| 赛程与体能 | 两个值都是修正值 | 双方休息天数、是否背靠背、近 4 晚和 6 晚的比赛数、上一场到本场的旅行距离（按球馆坐标计算）、跨越时区数、连续客场数 | 体能差异对分差和总分各修正几分 |

### 4.3 汇总块的三个版本

三个版本都能看到同一份参考盘口：主队让分值、总分线和各自赔率。

| 版本 | 能看到各块的哪些字段 | 输出 |
| --- | --- | --- |
| S-A 方向 | 只看 `lean` | 让分方向、大小分方向（含观望）和理由 |
| S-B 方向 + 把握 | 看 `lean` 和 `confidence` | 同上，另加整体把握 |
| S-C 方向 + 把握 + 分值 | 看全部字段 | 同上，另加预测分差和预测总分 |

- 汇总提示词统一要求：多个块的依据来自同一原因时不能重复叠加；让分和大小分分开判断，可以一个有方向、另一个观望。
- **程序基线 P0**：不调用模型。预测分差 = 实力块推算的分差 + 赛程修正，预测总分 = 节奏块推算的总分 + 赛程修正，再分别和盘口比较定方向。P0 的修正值用程序公式算，不用模型给的分值。P0 用来检验模型的解读有没有比直接计算更好。

## 5. 数据来源、清洗与存储

### 5.1 数据源验证结果（2026-11-11，在本机用 httpx 发只读请求，未使用任何 Key）

| 来源 | 结果 |
| --- | --- |
| NBA 官方 CDN（`cdn.nba.com` 的赛程和比分） | HTTP 403 Access Denied。可能是按 IP 或地区拦截，原因未确认 |
| NBA 官方统计（`stats.nba.com` 的球队比赛日志） | 两次都超过 60 秒没有响应 |
| **ESPN 公开接口 `scoreboard`**（按日期查询） | 可用。2026-03-10 返回 11 场，2026-11-10 返回 6 场。包含比赛 ID、UTC 时间、赛季与比赛类型、状态、主客队、球队缩写和全名、比分、是否中立场 `neutralSite`、球馆、每节比分（可判断是否加时） |
| **ESPN 公开接口 `summary`**（按比赛查询） | 可用。返回每队技术统计：投篮、三分、罚球、前场篮板、失误 `turnovers`、球队失误 `teamTurnovers`、总失误 `totalTurnovers` 等 |
| ESPN 日期范围查询 | 返回 HTTP 400，只能按天请求 |
| ESPN 伤病接口 `injuries` | 可用，有 28 队数据，包括球员状态和文字说明。可以作为第二批伤病块的候选来源 |

**结论：第一批用 ESPN 作数据源，用现有的 httpx 请求，不新增依赖。**

风险：ESPN 接口没有公开文档，也没有授权说明，返回格式可能随时变化或开始拦截。所以：
- 只做低频的个人研究请求，请求之间加间隔。
- 原始数据抓取后永久保存，不重复抓取。
- 程序里按“数据源”单独封装，以后可以换成其他来源，只改这一处。

### 5.2 需要什么数据、请求多少次

| 数据 | 范围 | 请求方式 | 估算次数 |
| --- | --- | --- | --- |
| 赛程和比分（算 Elo 用） | 2025-26 全季加本季至今 | `scoreboard` 每天 1 次 | 上季约 170 次；本季每天 1 次 |
| 每队每场技术统计（算回合数用） | 本季全部；上季用来给季初的节奏指标作参考 | `summary` 每场 1 次 | 本季每场 1 次；上季全季约 1230 次 |
| 球馆坐标和时区 | 30 队 | 手工整理成固定表 | 0 次 |

- 首次补齐历史数据大约需要 1400–1600 次请求。每次间隔 1–2 秒，约 30–60 分钟，只做一次。之后每天只增加新完场的比赛。
- ESPN 的赛季编号用结束年份。比如 2026-27 赛季在 ESPN 是 `year=2027`，入库时统一换成 `2026-27`。

### 5.3 清洗规则

1. **球队对照表**：建一张表，对齐 ESPN 的球队 ID 和缩写、The Odds API 的英文全名、中文名。跨来源匹配同一场比赛时，用主队、客队和开赛时间三者一起匹配，开赛时间允许几小时的误差。
2. **时间**：统一按 UTC 存。休息天数和背靠背按**美国东部时间的日期**算，不按北京时间算。
3. **比赛类型与主场**：只用常规赛（`season.type=2`）计算指标，NBA 杯阶段和是否中立场分别标记。主场优势只在确认是中立场（`neutralSite=true`，并核对实际球馆）时记为 0；在球队主场进行的杯赛保留主场修正，不能仅凭“淘汰赛”标签归零。场地标记缺失或与实际球馆冲突时，标为待核对，不猜测主场优势。杯赛规则按赛季核对：自 2026-27 赛季，半决赛在较高种子球队主场举行，只有决赛是中立场，不能套用此前半决赛在中立场的规则（[NBA 官方公告](https://pr.nba.com/nba-cup-semifinal-host-sites-coachs-challenge-rules)）。
4. **加时**：每节比分超过 4 节就是加时。节奏指标换算成每 48 分钟；总分照常包含加时。
5. **回合数**：回合数 ≈ 出手数 + 0.44 × 罚球数 − 前场篮板 + 总失误。总失误用 `totalTurnovers`，因为它包含球队失误。这个选择开发时用样例数据核对。
6. **校验**：
   - 每场正好两队数据。
   - 技术统计里的得分和比分一致。
   - 主客队和赛程一致。
   - 回合数在合理范围内。
   - 不通过的比赛单独标出，不修正也不删除。
7. **只用当时能拿到的数据**：计算某场比赛的指标时，只用这场开赛前已完场的比赛。用自动测试检查，违反了直接报错。
8. **重复抓取**：同一场比赛重新抓取时，按比赛 ID 覆盖，不新增重复行。原始数据另外按抓取时间保留。
9. **缺失数据**：标为缺失，不用平均值之类的数字补。

### 5.4 存储分三层

```text
原始层  data/raw/espn/{接口}/{日期或比赛ID}.json   原样保存，只追加，可随时重新清洗
标准层  data/clean/teams.csv  games.csv  team_game_stats.csv  odds_snapshots.csv   各块共用
特征层  data/features/strength.csv  pace.csv  schedule.csv   每块一个计算程序、一张表
```

各块不单独存原始数据，因为底层数据是共用的。赛程同时给实力块和赛程块用，技术统计同时给实力块和节奏块用，各存一份会出现数据不一致，清洗也要重复做。每块的独立性体现在特征层：各有自己的计算程序、特征表和提示词。以后加伤病块，只要增加伤病的原始数据、标准表和这块的特征程序，已有的块不用改。

## 6. 记录方式

推荐用 **CSV 加原始 JSON**：

- **CSV**：每块一个表，能直接用 Excel 打开、筛选和排序，适合人工复盘。统一用 UTF-8 BOM 编码保存，这样 Excel 打开时中文不会乱码。
- **原始 JSON**：每次调用模型都存一份完整记录，包括输入数据、提示词、模型原始回答和 token 用量。复盘时可以追查任意一条结论是怎么来的。
- 暂时不用数据库。小批量阶段 CSV 最直观；以后选定数据库时，按同样的字段导入就行。

### 6.1 目录

```text
backend/app/prompts/blocks/          提示词，提交 Git，按版本号命名
  strength_v1.md  pace_v1.md  schedule_v1.md
  summary_A_v1.md  summary_B_v1.md  summary_C_v1.md
data/experiments/{批次号}/           实验记录（目前 .gitignore 只忽略 data/odds/ 和 data/app/，是否忽略见第 10 节）
  runs.csv  games.csv
  block_strength.csv  block_pace.csv  block_schedule.csv
  summary.csv  review.csv
  raw/{比赛ID}_{块}_{第几次}.json
```

所有表用 `run_id`（批次号）和 `game_id`（比赛 ID）关联。

### 6.2 各表字段

| 表 | 一行是什么 | 主要字段 |
| --- | --- | --- |
| runs.csv | 一个批次 | run_id、创建时间、模型名、各提示词版本、数据快照时间、参考平台、每块重复几次、备注 |
| games.csv | 一场比赛 | game_id、开赛时间（UTC 和北京时间）、主队、客队；分析时的让分、总分及赔率与报价时间；收盘的让分、总分与报价时间；最终比分、是否加时 |
| block_*.csv | 一块 × 一场 × 一次重复 | run_id、game_id、第几次、提示词版本、各项输入指标（一项一列）、第 4.1 节全部输出字段、token 用量、耗时、错误信息、raw 文件路径 |
| summary.csv | 一个汇总版本 × 一场 × 一次重复 | run_id、game_id、版本（S-A/S-B/S-C/P0）、第几次、让分方向、大小分方向、把握、预测分差、预测总分、理由、token 用量、耗时 |
| review.csv | 一条结论 × 一场的结算 | 按分析时盘口和按收盘盘口分别结算让分、大小分（赢、输、走盘）；CLV（收盘盘口相对分析时盘口的变动分数）；预测分差误差和收盘盘口误差；人工打分（逻辑 1–5、有没有编造数据）；备注 |

- 让分符号约定：`spread_home` 是主队的让分值，-5.5 表示主队让 5.5 分；市场预期的主队净胜分 = -spread_home。
- 因素块不看盘口，复盘时按玩法分别计算实际结果相对收盘盘口的偏差，检查因素方向与偏差方向是否一致；这是诊断记录，单场一致不能证明该块提供了市场之外的信息。
  - 让分：`actual_margin = home_score - away_score`；`spread_residual = actual_margin + closing_spread_home`。偏差为正表示主队覆盖让分，为负表示客队覆盖让分。例：主队让 5.5 分、最终赢 3 分，偏差是 `3 + (-5.5) = -2.5`，应对应客队方向，不能直接用分差减去主队盘口值。
  - 大小分：`total_residual = home_score + away_score - closing_total`。偏差为正对应高分方向，为负对应低分方向。
  - 偏差为 0 时记为走盘，方向一致性标为“不适用”；因素方向为 `neutral` 或 `insufficient` 时也不纳入方向一致率。缺少该玩法的收盘盘口或最终比分时，偏差及一致性记为缺失，不按 0 或输盘填充，也不影响另一玩法独立评估。
  - 结算某条预测时，要结合它选择的主队/客队或大/小方向判断赢输；客队与小分的赢输方向和上述偏差符号相反。按分析时盘口结算时使用同一公式，替换成分析时的盘口；收盘盘口缺失不影响已有分析时盘口的结算。

## 7. 测试安排

| 项目 | 安排 |
| --- | --- |
| 场次 | 第一批 10–15 场，也就是 1–2 个比赛日 |
| 比赛 | **只测未开赛的比赛**。不用已结束的比赛回测，因为模型可能已经知道赛果，结论会被污染 |
| 重复次数 | 每块和每个汇总版本各跑 2 次，检查同样输入下结论稳不稳定 |
| 调用次数 | 每场 (3 块 + 3 个汇总版本) × 2 次 = 12 次，15 场约 180 次。实际 token 费用按记录统计，不预估 |
| 盘口 | 分析时用当时的快照；每个比赛日开赛前再取一次作为收盘盘口。每天开赛时间不同时可能要取 2–3 次，每次约 2 credits |
| 参考平台 | 固定一个平台，选快照里覆盖比赛最全的那家，记进 runs.csv |
| 收盘盘口 | 开赛前最后一次快照，记录报价时间；没有取到的标为缺失 |

## 8. 小批量能验证什么

**能验证**：
- 流程是否完整跑通。
- 模型是否只用了给它的数据，有没有编造伤病或赛果。
- 同样的输入，两次结论是否一致。
- 每块的理由和它拿到的指标是否对得上。
- 三种汇总版本的结论差别有多大。
- 实际费用和耗时。

**不能验证**：哪种表达方式“更准”。15 场比赛的命中率波动太大，比如 100 场、命中率 50% 时，95% 置信区间大约是正负 10 个百分点，15 场就更宽了。所以第一批**不能用命中率决定选哪种方式**。要分出高下，需要连续积累几百场，再看 CLV、分差误差和把握是否和实际结果相符。

## 9. 开发步骤

每一步都有验收标准，完成一步再做下一步。凡是要花钱的调用（模型或盘口 API），执行前先和你确认。

| 步骤 | 内容 | 验收标准 |
| --- | --- | --- |
| 1 | 数据抓取和清洗：按第 5 节，从 ESPN 抓两个赛季的赛程、比分和技术统计，存原始层，清洗成标准层。可访问性已验证：NBA 官方接口在本机不可用，ESPN 可用（见 5.1） | 标准层数据通过 5.3 的校验；人工抽查 3 场，比分和技术统计与 ESPN 网页一致 |
| 2 | 三块指标的计算程序，加离线单元测试（用固定样例数据） | 测试通过；人工抽查 2 场比赛，指标和公开数据一致 |
| 3 | 写好 v1 提示词：3 个因素块和 3 个汇总版本 | 你审阅通过 |
| 4 | 批量运行脚本：选场、计算指标、调用模型、写 CSV 和原始 JSON。复用现有的 `request_model`；失败只记录，不自动重试 | 先用 1 场试跑，CSV 字段完整；确认后再跑整批 |
| 5 | 收盘盘口和结算脚本：补收盘盘口；用 The Odds API 的 `/scores` 接口在 3 天内取比分；生成 review.csv | 结算结果和人工核对一致 |
| 6 | 复盘：你在 review.csv 里人工打分，我整理一页结论 | 决定第二批加哪些块、提示词要怎么改 |
