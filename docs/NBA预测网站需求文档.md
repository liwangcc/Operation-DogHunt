本节表格是你已经确认的方向；后面的页面、规则与实现顺序属于初稿建议，需要继续讨论。

几个词先说清楚：Agent 像一个会使用工具的 NBA 助手，能按你的请求查询资料、分析并接着聊。API 是程序连接外部服务的通道；GPT API 提供 AI 能力，比赛与盘口 API 提供真实体育数据，两者职责不同。上下文是它本轮答题时能看到的资料；长期记忆是跨聊天保留、需要时再取出的笔记。父块像笔记目录，子块是具体条目。

AI 综合分析，就是把已收集的资料交给 AI，让它给方向和理由；统计模型，就是用历史数据学出一套计算方法。盘口快照像给盘口拍照，保存当时的数值、赔率和时间；回测则是按过去当时能知道的信息，模拟检验一种方法。策略版本指一套具体的分析要求和选择规则，规则变了就另存一版，方便比较。

## 2. 产品要解决什么问题

打开网站后，可以直接说“帮我看看今天的比赛”。Agent 返回真实赛程、让分和大小分卡片；选择比赛后继续分析，也可以自然追问、比较和复盘。

产品的核心交互是聊天，赛程、盘口、分析和统计以卡片嵌在聊天中，独立页面提供查看完整记录的入口。

第一版需要形成一个完整流程：

**用户提问 → 识别意图与相关记忆 → 查询真实赛程和盘口 → 用户选比赛 → 补齐赛前资料 → GPT 分析 → 保存当时版本 → 继续追问或赛后复盘。**

核心验证问题：在预测当时可获得的盘口和赔率下，系统的判断是否具有可重复的价值。仅统计比赛胜负或展示几场命中，无法回答这个问题。

### 建议的首版边界

- 做个人分析与模拟验证工具，提供中文界面，电脑优先、手机可正常查看。
- 首先覆盖 NBA 常规赛及季后赛；季前赛、全明星赛暂缓。
- 只分析赛前全场标准让分盘、全场标准总分盘；半场、单节、滚球、球员个人数据玩法后续再评估。
- 全场暂按含加时的市场设计，具体必须与所选数据来源的市场定义及结算规则一致。
- 首版提供预测与模拟记录；真实投注、账户资金、支付、会员和社区不纳入本轮需求。
- 本地使用可以直接进入；如部署到公网，至少使用单用户访问保护。

## 3. 日常使用流程

| 用户怎么说或怎么操作 | Agent 应该怎么做 |
| --- | --- |
| “帮我看看今天的比赛” | 按北京时间查询赛程，列出对阵、开赛时间、全场让分、总分线、两侧赔率和来源时间；等待用户选择 |
| 点击一场，或说“看第 2 场” | 绑定该条列表中对应的比赛，补充最新球队与伤病资料，分析全场让分和大小分 |
| “这场只看大小分” | 保持同一场比赛，缩小分析范围，不重新猜测指的是哪一场 |
| “如果主力不上呢？” | 在原比赛下做明确标记的假设分析，不把假设当成已确认伤病 |
| “再和另一场比一下” | 明确第二场比赛，使用可比较的报价时间与规则，说明两场差别 |
| “刷新一下盘口再看” | 重新查真实盘口并生成新分析，保留上一个版本 |
| “昨天那场结果怎么样” | 查已保存的预测和真实赛果，按当时盘口复盘；指代不清时先确认 |
| “以后先给结论，再讲原因” | 自动更新输出偏好，展示已记住的提示，后续聊天使用该偏好 |

“今天”由程序根据北京时间解析成具体日期，并随查询结果显示；跨午夜后再次说“今天”需要重新解析。没有比赛、未开盘、未取得伤病数据时，如实显示。

## 4. 网站页面

首页直接进入 **NBA 助手聊天**。建议侧栏提供：新聊天、历史聊天、预测记录、效果统计、记忆管理、设置。赛程卡片和比赛详情嵌在对话中，也能打开独立详情。

### 4.1 Agent 聊天首页

- 中间是聊天记录，底部是输入框；提供“今天的比赛”“继续上次分析”“查看预测表现”等快捷入口。
- 首次进入不强制填写表单。需要补充信息时，在对话中简短询问。
- 查询比赛后展示可选择的比赛卡片；选择后再发起深入分析。
- 执行中显示真实阶段：查询赛程、获取盘口、补齐资料、AI 分析、保存结果。
- 回答逐步显示，让用户先看到已有内容；提供停止、失败后重试、刷新数据入口。
- 刷新页面能恢复聊天记录和后台任务状态；不能因为刷新页面就再付费调用一次 GPT。
- 聊天历史支持重命名、查找和删除入口；永久删除的范围与确认方式需单独定义。

每张赛程卡片展示：

- 主客队、开赛时间、状态。
- 全场让分、全场总分线及两边赔率。
- 参考平台、数据更新时间、选择或查看详情按钮。

仅列赛程时不自动深入分析全部比赛，不自动为每场产生正式预测。数据卡片数值由真实接口结果填充，不能由 GPT 补写。

### 4.2 比赛详情与分析卡片

每场比赛展示：

- 比赛日期、北京时间、主客队、比赛状态。
- 当前参考平台名称；让分及双方赔率；总分线及大、小双方赔率。
- 让分判断：主队方向、客队方向、观望或数据不足。
- 大小分判断：大分、小分、观望或数据不足。
- AI 的主要理由和不确定因素。首版建议先不显示未经检验的数值命中概率；是否展示 AI 估计比分，另行讨论。
- 预测生成时间、盘口来源更新时间、数据是否完整。
- 正式预测是否已锁定。

支持按日期切换；按玩法、预测状态筛选。无比赛、未开盘、接口异常应有明确状态。

分析详情分成四部分：

| 区域 | 内容 |
| --- | --- |
| 盘口 | 当前让分、总分和赔率；正式预测时使用的盘口快照 |
| 判断 | 两个玩法分别给出 AI 方向、观望原因、主要依据及版本 |
| 依据 | 球队近期表现、主客场、进攻防守、节奏、休息时间、伤病等已有数据 |
| 复盘 | 赛后比分、输赢走盘结果、模拟盈亏、自己的笔记 |

盘口变化首版至少保留采集快照；完整走势图可后续增加。首次采集到的盘口标记为“首次采集盘”，只有确实取得开盘数据才能标记为“开盘”。

解释应呈现主要支持因素和不确定因素，并能追溯到数据。没有可靠数据时，不生成“资金大量流入”“庄家诱导”“内部消息”等事实性结论。

### 4.3 预测记录与聊天历史

- 列出赛前已经保存的所有正式预测，包括赢、输、走盘、取消及待结算。
- 可按日期、球队、玩法、策略版本和结果筛选。
- 展示当时的方向、盘口、赔率、参考平台、生成时间、结算结果。
- 支持导出 CSV（一种可以用 Excel 打开的表格文件），便于独立核对。
- 个人判断与系统判断分别保存、分别统计，不能覆盖系统记录。
- 预测能跳回生成它的聊天，聊天中的分析能打开对应快照。
- 新聊天可以引用明确选中的历史分析，但不自动把全部聊天塞进新对话。

### 4.4 效果统计

- 分别展示让分、大小分的表现，可查看总体汇总。
- 展示已分析比赛数、有效选择数、观望数、数据不足数及结算分布。
- 展示命中率、累计模拟盈亏、模拟 ROI 和累计盈亏曲线。ROI 就是赚亏占投入的比例，例如投入 100、净赚 5，ROI 为 5%。
- 筛选时间范围和策略版本；所有比例同时显示样本数。
- 历史回测、上线后的真实赛前记录、人工补录分别统计。

### 4.5 记忆管理

- 用“父块目录 → 子块条目”的方式查看已记住的内容。
- 展示记住了什么、来自哪次聊天、何时更新、是否过期。
- 提供修改、停用、忘记、查看归档入口；自动保存后允许撤销。
- 本次回答使用了哪些记忆，可展开查看。
- 维护记录说明合并、过期、冲突和归档情况，不把后台维护动作当作用户发言。

### 4.6 设置与运行状态

- 数据源、参考平台、时区、赔率显示格式。
- GPT 模型、超时与重试限制、使用额度及费用提醒。
- 预测时间与正式记录规则。
- 数据同步时间、接口失败、缺失数据和剩余额度（来源支持时）。
- API 密钥相当于访问密码，只保存在网站后台，不写入聊天、长期记忆或普通日志。

## 5. 两种预测具体输出什么

### 5.1 让分预测

必须明确预测的是“对应盘口下能否赢盘”，不能用“哪支球队获胜”代替。

每条记录包含：比赛、被选球队、该球队的让分或受让数值、赔率、参考平台、预测时间、AI 方向、依据及不确定因素。

例如：主队 A 让 5.5 分，即使 AI 看好 A 获胜，也必须单独判断 A 能否赢到 6 分以上。比赛获胜方与让分判断可能不同。

### 5.2 大小分预测

每条记录包含：比赛、总分线、大或小的方向、对应赔率、参考平台、预测时间、AI 依据及不确定因素。

例如：盘口总分 225.5，AI 需要结合两队进攻、防守、节奏、伤病及盘口作出判断。如果它估计总分为 220，这仍只是估计，不能直接解释为某个已验证的赢盘概率。

以上数字均为功能示例，不代表实际比赛预测。

### 5.3 输出规则

- 同一比赛的让分和大小分分别判断，可以一个有方向、另一个观望。
- 建议允许“观望”，不强制每场每个玩法都给选择；具体条件待确认。
- 预计分差或总分偏离盘口多少分，与赢盘概率是两个不同指标，不能直接互换。
- 首版建议以方向、依据、不确定因素为主，不把 AI 主观打分当成“真实命中概率”。
- 未来加入经过验证的概率模型后，整数盘口需区分赢盘、走盘、输盘，三者概率之和为 100%。
- 赔率、盘口、方向必须属于同一平台、同一市场和同一可用快照，不能拼接出不存在的报价。
- 盘口变化后，旧预测仍按旧盘口保留；新分析创建新版本，不覆盖历史。

## 6. 需要哪些数据

| 数据 | 用途 | 首版要求 |
| --- | --- | --- |
| NBA 赛程与状态 | 展示、安排预测、确认是否完场 | 必需 |
| 全场让分及双方赔率 | 让分判断与结算 | 必需 |
| 全场总分及大、小赔率 | 大小分判断与结算 | 必需 |
| 平台、市场定义、更新时间 | 确认报价和结算适用范围 | 必需 |
| 最终比分、加时信息 | 赛后结算 | 必需 |
| 历史比赛、球队表现 | 给 AI 提供近期和赛季背景 | 必需；具体指标取决于数据覆盖 |
| 休息天数、背靠背、主客场 | 赛前特征 | 首版基础信息 |
| 伤病、出场状态 | 调整判断、提示不确定性 | 优先接入；缺失必须标记 |
| 历史盘口与赔率快照 | 按当时条件回测 | 有合格数据后才能做对应历史回测 |
| 可靠的投注比例或资金流数据 | 额外研究 | 后续评估，不能从盘口涨跌直接推导 |

跨来源需要统一比赛和球队标识，不能只按中文名称匹配。所有时间内部统一保存 UTC（统一的国际计时基准），界面默认按北京时间展示。

### 数据来源依据与后续补齐

[The Odds API 官方文档](https://the-odds-api.com/liveapi/guides/v4/#get-odds)提供 `spreads`（让分）、`totals`（大小分）市场，以及平台、赔率、盘口数值和市场更新时间等字段。项目已用该服务完成最小盘口取数。

该服务的[历史赔率接口](https://the-odds-api.com/liveapi/guides/v4/#get-historical-odds)需要付费方案，且历史平台和市场覆盖取决于其实际收录情况。因此，不能预设免费的完整历史盘口一定可得。

最小取数已验证；持续使用前还需确定更新频率、长期额度与预算，并核对目标平台、报价延迟及历史覆盖。球队表现、伤病和完整赛程仍需单独核对，不能把盘口接口首次成功扩大为全部数据已齐备。

建议先选一个固定参考平台，避免各场临时选择不同平台导致结果难以比较；多平台比价后续再做。

## 7. 预测怎样产生

**已确认：第一版是接入 GPT API 的 NBA Agent，采用 AI 综合分析，未来再评估与统计模型结合。**

可以把第一版理解为：GPT 判断需要查什么，网站后台提供查询工具并执行，资料返回后 GPT 分析，再把可核对的结果呈现给用户。Function calling 就是 GPT 以固定格式提出“调用哪个工具、传哪些参数”，实际查询由网站后台完成。

### 7.1 Agent 的工作范围和工具

| 工具能力 | 要完成的事 | 关键限制 |
| --- | --- | --- |
| 查赛程 | 返回指定日期的 NBA 比赛和状态 | 明确日期与时区 |
| 查盘口 | 返回所选比赛的全场让分、总分及赔率 | 统一来源、快照和市场规则 |
| 查球队与伤病 | 返回赛前可用资料 | 带来源、时间及缺失项 |
| 查历史分析与赛果 | 找回旧判断并复盘 | 历史盘口与当前盘口分别标明 |
| 读写记忆 | 按父块、子块取回或更新相关偏好和研究笔记 | 记忆有来源和适用范围 |
| 保存分析 | 保存完整分析、输入和数据快照 | 重试不重复写入 |

后台检查比赛标识、日期、参数和工具权限；GPT 不能任意调用未提供的工具。外部资料与记忆中的文本按资料处理，不能用来改写系统规则。

第一版的请求是“先展示赛程再选择”，因此 Agent 应停在比赛选择步骤，不能自行扩大成分析所有比赛。

### 7.2 提供给 AI 的资料

- 比赛身份、主客队、开赛时间。
- 当前参考平台的让分、总分线、两边赔率及更新时间。
- 已取得的近期比赛和赛季表现、主客场表现、进攻防守及节奏信息。
- 休息时间、背靠背、伤病和出场状态；缺失项明确标记。
- 已有盘口快照。没有更早的快照，就不能要求 AI 判断“从开盘到现在”的变化。

首版建议让 AI 只依据资料包里的事实分析，避免它凭记忆声称知道最新伤病或盘口。数值计算、结算及统计由程序完成。

### 7.3 要求 AI 返回的内容

| 内容 | 要求 |
| --- | --- |
| 让分结论 | 被选球队及对应盘口，或观望、数据不足 |
| 大小分结论 | 大分或小分及对应总分线，或观望、数据不足 |
| 核心依据 | 每个玩法列出主要依据，并引用资料包中的对应数据 |
| 不确定因素 | 例如关键球员出场未定、信息缺失、数据互相矛盾 |
| 简短说明 | 用中文说明判断过程，便于自己快速阅读 |

### 7.4 保证后续能核对

- 保存使用的 AI 服务、具体模型、提示词版本、输入资料和原始输出。提示词就是交给 AI 的分析要求，类似一张固定的答题说明。
- 同一资料可能得到不同回答，因此正式记录按固定时点保留，不能反复重试直到出现想要的结论。
- AI 返回了不存在的盘口、球队或资料包之外的事实时，该次分析标记异常，不直接变成有效选择。
- AI 调用失败、无法解析或资料不足时，展示明确状态；重试不能覆盖已经锁定的正式记录。
- 记录调用次数和费用估算，便于控制每天的使用成本。
- 分析效果尚未验证时，界面标记“实验预测”。AI 自述的“信心 80%”不等于已经验证的赢盘概率。

AI 服务已确定为 OpenAI 的 GPT API；具体 GPT 模型、分析模板和调用预算尚未选择。单个 Agent 不等于只能调用一次 GPT，一个任务可以经过若干次有上限的工具与模型调用。

### 7.5 GPT API 接入依据

建议评估 Responses API，它是 OpenAI 提供的模型交互接口，支持本产品需要的工具与对话能力；具体接续方式在实现前确定。本节只说明已核对的能力，不代表已完成集成。

- [Function calling](https://developers.openai.com/api/docs/guides/function-calling)：由模型提出工具请求，应用执行并返回结果，符合查询体育数据再分析的流程。
- [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)：支持自行管理历史或使用接口提供的对话衔接。对话接续仍需考虑内容长度和费用，不能当成免费、无限的记忆。
- [Streaming](https://developers.openai.com/api/docs/guides/streaming-responses)：可以在生成过程中逐步返回内容。Streaming 就像边写边展示，但收到一段文字不等于整次分析成功。
- [Compaction](https://developers.openai.com/api/docs/guides/compaction)：可压缩长对话用于接续；接口的压缩状态与产品中可查看的长期记忆是两件事，不能互相替代。
- [Rate limits 与重试](https://developers.openai.com/api/docs/guides/rate-limits#retrying-with-exponential-backoff)：临时限流可延迟重试，需要限制次数和总耗时，避免开发工具内置重试与业务重试叠加。

## 8. 上下文怎么接住

上下文像 AI 本次答题时桌上的资料，桌面有大小限制；聊天历史保存在系统里，不代表每次都要全部摆到桌上。

### 8.1 每个聊天单独保存状态

- 保存当前选中的比赛、玩法、参考平台、报价快照、日期与时区、用户补充条件、任务进度。
- 赛程列表有自己的版本和比赛标识。“第 2 场”指向用户看到的那一版列表，不会因新列表排序变化而指错比赛。
- “这场”“刚才那场”优先指向当前明确选中的比赛；存在多个合理对象时先问清楚。
- 新聊天默认不继承另一聊天正在分析的比赛或未完成任务；跨聊天只召回相关长期记忆和明确引用的历史记录。
- 同一聊天并发输入需要按顺序处理。新的补充条件不能偷偷修改已经在执行的那一版任务。
- 刷新页面或重新登录后，根据保存的状态恢复聊天与任务；只有聊天列表、没有任务状态，不算完成恢复。

### 8.2 每次请求按需拼装资料

建议按以下顺序给 GPT 提供内容：产品规则 → 当前请求和比赛状态 → 最近对话 → 历史对话摘要 → 相关父子记忆块 → 本次查询的赛前数据。

长期记忆只提供与问题有关的部分；所有模块都受总长度限制。Token 是 API 计算文字量的单位，不等于一个汉字；使用所选模型对应的计数方式，预留回答和后续工具结果空间。

### 8.3 长对话压缩

- 建议在输入达到可用上下文预算的 70% 时准备压缩，具体阈值接入后调整；不能等到接口报长度超限才处理。
- 摘要保留：用户明确要求、当前比赛与玩法、重要条件、尚未回答的问题、已完成步骤、引用的来源和快照标识。
- 原始聊天与原始快照继续保留，摘要只是便于接续的目录，不替代原始记录。
- 已经发起的工具请求与返回结果要配对保存；不能截掉一半后继续调用。
- 摘要中不能把用户的假设写成事实，也不能把 AI 的历史结论写成用户偏好。
- 失败或取消任务的部分输出标记为未完成，不能作为已确认结论写入摘要或长期记忆。
- 压缩失败时保留旧摘要，缩小本次召回范围；仍无法容纳时，明确提示新建聊天并携带精简交接，不无限重试。
- 删除或停用记忆后，后续上下文和旧摘要也要停止引用它；必要时重建对话接续，避免从旧 API 对话链中再次带回。

### 8.4 历史与当前数据分开

旧聊天里的盘口和伤病可用于解释过去的判断，不能作为当前报价。用户追问“现在还能看这个方向吗”，要重新检查实时性并按需查询；新分析引用新快照，旧分析继续保留旧快照。

## 9. 长期记忆：父块、子块和维护

**已确认：自动保存，并定期清理维护。**下面是建议的组织和维护规则。

### 9.1 记忆结构

| 父块示例 | 子块示例 | 作用 |
| --- | --- | --- |
| 用户输出偏好 | 先给结论再讲原因、赔率格式、常用时区 | 跨聊天保持使用习惯 |
| NBA 分析偏好 | 优先看全场让分和大小分、希望比较哪些因素 | 保持关注范围，不干预客观结论 |
| 比赛研究 | 某场的用户假设、待核实问题、已引用的分析版本 | 按比赛查回相关研究，不当成实时数据 |
| 复盘笔记 | 用户记录的观察、待检验的分析经验 | 区分已核实事实与尚未验证的想法 |

父块保存简短摘要、主题、子块目录和更新时间。子块一条尽量只讲一件事，保存所属父块、正文、来源聊天或记录、适用对象、更新时间、有效期、状态及版本。

内容变长或出现多个主题时拆成更多子块；父块的摘要也有长度上限，不能把全部子块重新堆成一大段。

### 9.2 自动保存和纠错

- 对用户明确表达的稳定偏好自动保存，显示“已记住”的简短提示，并提供撤销入口，不逐条打断询问。
- 只有记忆保存成功才提示“已记住”；保存失败显示待保存状态，后台有限重试，不能假装已经记住。
- 从单次行为猜出的偏好标记为候选，不能直接当作确定要求。例如点了一次小分，不代表用户永远偏好小分。
- 用户新的明确要求优先于旧偏好；旧版本标记为被替代，保留来源以便核对。
- AI 生成的分析和经验以“AI 判断”或“待验证研究”保存，不能升级成客观事实。
- 偏好不改变真实数据和结算规则；用户希望看大分，也不能因此把所有结论写成大分。
- 盘口、伤病等有时效的信息保留来源和有效期；长期记忆不承担实时行情缓存的职责。
- API 密钥等访问凭证不保存到记忆。

### 9.3 怎么查回来

先通过父块主题找目录，再取相关子块，必要时继续展开；结合比赛标识、时间、来源和有效期筛选。每次召回有数量与 Token 上限，超出后按相关性取舍，不直接载入全部记忆。

回答引用某条记忆时，能查看对应来源。找不到可靠记录时说明不确定，不能为了“显得记得”而补写。

### 9.4 定期维护

建议由产品后台每天低峰维护一次，并在单个块过大时触发拆分。这是网站要实现的功能，本轮没有创建实际定时任务。

- 检查过期、重复和冲突条目，合并同义内容，拆分过大的块。
- 子块更新后，同步更新父块摘要和检索目录；失败时不把半更新状态投入召回。
- 稳定偏好保留到被修改或停用；比赛研究在赛后转为历史资料，不再作为赛前现状召回。
- 长期不用的临时笔记可先归档，归档期限待确认；清理维护首版建议采用可恢复归档，永久删除与保留期限另行确认。
- 正式预测、原始盘口快照和结算证据独立保存，记忆维护不能改写这些记录。
- 维护过程有日志；失败不阻塞主聊天，下一次有限重试。
- 用户选择“忘记”后，后续召回应立即排除对应内容，并清理派生摘要和索引；上游 API 存储的处理方式按实际接入能力确定，不能只删除界面上的一行。

## 10. 超时、异常和恢复

目标是任何请求都有可见状态、耗时上限和明确出口。某一步失败不必把已查到的赛程一起丢掉，也不能把半段生成文字当成完整预测。

### 10.1 建议的初始限制

以下是产品建议值，**不是 OpenAI 的默认值或响应速度承诺**。具体 GPT 模型、数据源和部署方式确定后，需要用实际请求调整。

| 限制 | 建议初值 | 到达后怎么处理 |
| --- | --- | --- |
| 界面确认收到请求 | 1 秒内显示本地发送或排队状态 | 不让用户误以为没有发送 |
| 单次上游连接建立 | 10 秒 | 标记连接失败，按剩余预算决定是否重试 |
| 单次体育数据请求 | 10 秒 | 返回该数据项失败，其他已取得的数据保留 |
| 同一数据步骤总时间 | 25 秒，含等待与重试 | 停止该步骤，必要数据缺失则不生成有效选择 |
| GPT 单次调用总时间 | 90 秒 | 停止等待该次调用，保存已知请求状态 |
| 上游连续无任何有效事件 | 45 秒 | 判为疑似中断并查询已知状态；界面心跳不能冒充上游进展 |
| 用户暂时没看到回答正文 | 30 秒 | 提示当前真实阶段；不是自动判定任务失败 |
| 一项完整分析任务 | 180 秒，含查询、模型、重试和等待 | 结束为超时或部分完成，保留已完成步骤 |
| 同一外部调用总尝试次数 | 最多 2 次，即首次加 1 次重试 | 不再自动重试，提供手动恢复入口 |

所有子步骤受完整任务的剩余时间约束，连接建立时间也包含在该次请求的时限内。重试、压缩或断线重连不能把总计时重新归零。

### 10.2 按错误类型处理

| 情况 | 产品规则 |
| --- | --- |
| 短暂网络错误或服务端故障 | 在次数和总时间内延迟重试；优先只重试失败步骤 |
| 临时限流 `429` | 按服务端建议等待；有 `Retry-After`（服务端要求等待的时间）时不得提前重试。等待会超出剩余预算则结束并说明稍后再试 |
| 余额不足、额度用尽、密钥无效或权限错误 | 不循环重试，明确提示需要检查哪一类设置 |
| 参数不正确或工具不存在 | 拒绝执行；可修正一次，计入同一任务预算 |
| 上下文过长 | 先压缩或减少无关记忆，再有限重试，保留当前比赛与用户约束 |
| GPT 返回格式无法使用 | 检查固定字段，最多一次纠正；未通过不能保存为有效预测 |
| 返回不存在的比赛、盘口或来源 | 按实际数据核对并判定异常，不直接展示成事实 |
| 只有部分数据或部分比赛成功 | 标明哪些已完成、哪些缺数据；缺少关键盘口的玩法不能强行给有效选择 |
| 回答因长度限制而中断，或没有完成事件 | 标记为未完成；不静默接成“已完成”，恢复仍受预算限制 |
| 模型明确无法完成分析 | 展示原因和已知信息，不通过无限重试逼出结论 |

若业务层统一控制重试，开发工具库的内置重试应关闭或纳入同一计数，避免表面“重试一次”，实际发送很多次。

### 10.3 断线、停止和重复提交

- 请求开始时创建任务编号，执行阶段与结果保存在后台，不只存在浏览器内存中。
- 用户断网或刷新后，重新查询原任务并恢复展示；不能直接再创建一项相同任务。
- 用户点击停止，任务进入已取消状态，停止后续工具调用，并尽可能取消正在等待的上游请求。上游已经处理的调用仍可能产生费用，不能承诺停止就不计费。
- 已知 GPT 响应编号时，先按可用接口核对状态；超时不等于服务端一定没处理，不盲目重复提交。
- 重复点击、网络自动重发和任务重试不能重复保存预测或记忆变更。这称为幂等：同一个业务动作重复到达，也只产生一次有效保存。
- 如果第一次调用没有拿到响应编号，无法绝对保证上游没有执行；系统记录这种不确定性，限制重试并提醒可能重复产生调用费用。
- 只有收到完成状态、字段检查通过并成功保存，才能标记为完成。部分文字和失败消息不得写进正式预测统计。
- 恢复前检查数据是否已经过期或比赛是否开赛；需要新数据时创建分析新版本，不伪装成原先按时完成。

任务状态至少包括：排队中、查数据、AI 分析中、已完成、部分完成、失败、超时、已取消。状态与提示由真实任务事件驱动，不生成虚假的“正在查询”过程。

## 11. 控制执行范围和费用

Agent 要能自己调用工具，也要有边界，避免重复查询或不断自我分析。以下为待实测的初始建议：

- 同一聊天一次执行一个任务，后续消息按顺序接入；用户可以停止当前任务再换目标。
- 单个分析任务最多 6 次 GPT 请求、12 次工具执行，总时间仍受 180 秒限制；重试和纠正计入次数。
- 所有请求都记录使用量；Token 上限、单任务费用上限和每天费用上限，在选定模型与预算后配置。费用估算与最终账单需分开标记。
- 达到任一上限就停止继续扩展，返回已完成内容与停止原因，不自行换更贵模型或扩大分析场次。
- 赛程列表共用同一次数据查询；选择一场后才获取它的深入分析资料，避免对所有比赛重复调用 GPT。
- 记忆提取、摘要和清理也计入成本，建议后台低优先级执行，不抢占主聊天的请求额度。
- GPT 模型、提示词和工具规则均保存版本；升级后与旧版本表现分别统计。

## 12. 赛前记录规则

以下为建议方案，时间参数可调整：

| 项目 | 建议规则 |
| --- | --- |
| 日常查看 | 展示最新可用盘口和试算，清楚标明时间 |
| 聊天分析 | 保存完整分析记录，但普通追问不自动增加一笔模拟投入 |
| 正式预测 | 触发方式与截止时间待确认：手动标记正式或定时锁定；原先的开赛前 60 分钟只是候选方案 |
| 正式记录数量 | 每场、每个玩法、每个策略只有一条纳入主统计的正式决定，包含观望 |
| 新信息 | 可生成更新分析，但不能追溯替换正式决定 |
| 报价有效性 | 显示采集时间和市场更新时间；新鲜度阈值根据数据试接结果确定 |
| 未开盘或报价缺失 | 对应玩法显示“数据不足”，不生成可结算选择 |
| 错过生成时间 | 标记为漏预测；补算记录单独保存，不当作按时产生的记录 |
| 开赛后 | 禁止把新生成记录写成赛前正式预测 |
| 改期或中断 | 保留原记录，按来源规则待核对；不直接算输或擅自改用另一场盘口 |

每次正式决定必须冻结：赛前输入、盘口快照、来源、赔率、生成时间、策略版本、模型版本及输出。手动修正只能追加修正记录，不能静默改写。

## 13. 赛后怎样结算

### 13.1 让分

对选择的球队计算：

**结算差值 = 该球队最终得分 + 该球队盘口数值 − 对手最终得分。**

- 大于 0：赢盘。
- 小于 0：输盘。
- 等于 0：走盘。

例：选择 A -5，A 最终赢 5 分，结果为走盘。负号、主客队和选择球队必须正确关联。

### 13.2 大小分

在该市场规定的比赛范围内计算双方得分之和：高于总分线时大分赢，低于总分线时小分赢，等于总分线时走盘。

含加时与不含加时不得混用。取消、延期、中断及特殊情况以保存的规则为准；无法确认时进入“待核对”，不强行结算。

### 13.3 模拟盈亏

建议统一以每个有效选择固定投入 **1 单位**做模拟，内部赔率统一存为十进制格式。十进制赔率 1.90 表示投入 1 单位，赢时连本金收回 1.90，净赚 0.90；香港盘水位 0.90 表示的也是净赢 0.90。

| 结果 | 模拟净盈亏 |
| --- | --- |
| 赢盘 | 十进制赔率 − 1 |
| 输盘 | −1 |
| 走盘 | 0 |
| 取消或无效 | 0，投入不计入 ROI 分母 |

页面明确标注“按记录盘口和赔率计算的模拟表现”。该统计不代表真实成交，也不与个人实际盈亏混在一起。

## 14. 如何验证有没有效果

| 指标 | 定义与展示要求 |
| --- | --- |
| 命中率 | 赢盘数 ÷（赢盘数 + 输盘数）；走盘与取消另列 |
| 模拟盈亏 | 所有已结算有效选择的净盈亏合计 |
| 模拟 ROI | 净盈亏 ÷ 已结算投入；含走盘投入，不含取消与待结算 |
| 选择覆盖率 | 有效选择数量 ÷ 符合分析条件的比赛玩法数量；同时披露观望和缺数据数量 |
| 概率质量 | 未来接入概率模型时再增加；首版 AI 定性分析不以主观信心分数代替 |
| 持续性 | 分时段、玩法和策略版本查看；避免只展示最好的一段 |

赔率不同，达到盈亏平衡所需的命中率也不同。因此不能把“超过 50%”直接定义为盈利。

EV 是预期收益，意思是假设同样条件重复很多次，平均每投入 1 单位预计赚亏多少。首版 AI 分析尚无可靠概率时，建议暂不显示数值 EV；未来具备经过验证的概率后，按下式计算：

**EV = 赢盘概率 ×（十进制赔率 − 1）− 输盘概率。**

其中走盘盈亏为 0，不能将含走盘的情形简化成输盘概率等于 1 减赢盘概率。概率本身没有通过验证时，EV 只能标记为实验估计。

### 历史回测与上线验证

- AI 历史回测存在一个额外问题：AI 可能已经知道过去比赛的结果，即使资料包删掉比分，也不能证明它完全不知道答案。因此首版以真正赛前保存的记录作为主要验证，历史模拟作为辅助参考。
- 未来加入统计模型时，训练、验证、测试按比赛时间切分。好比用较早的比赛练习，再留后面的比赛当考试，不能边看答案边改方法。
- 历史判断只可使用当时已公开的数据。赛后修订的数据、后续盘口或后来确认的伤病不能倒灌。
- 历史盘口取预测截止时间之前的可用快照，并保留其真实时间。
- 若缺少历史赔率或当时的关键输入，只做具备证据的部分验证，不展示为完整投注回测。
- 如果暂时没有合格历史数据，先从上线日起积累赛前记录，历史表现显示“暂无数据”。
- 所有符合规则的正式决定都要保留，不能赛后删掉输盘记录或临时修改筛选规则再宣称旧策略有效。
- 功能验收与效果验证分开：首版先保证记录和结算可信，再通过足够样本判断预测方法是否有价值。暂不承诺目标命中率或收益率。

P0 表示第一版必须完成，P1 表示后续增强，P2 表示验证后再考虑。

## 16. 首版验收标准

1. 能按北京时间查看真实赛程，主客队和状态正确；未开盘仍可显示比赛。
2. 一场比赛可以同时显示让分及总分线、对应两侧赔率、平台和更新时间。
3. AI 能对两个玩法独立输出方向、观望或数据不足，并能查看输入资料、依据与分析版本。
4. 正式记录锁定后，刷新盘口、重新分析或重启服务都不会覆盖它。
5. 缺赔率、过期数据、错过生成时间和开赛后补算均有明确状态，不混入正常赛前统计。
6. 让分和大小分均能正确处理赢、输、走盘，含加时规则一致。
7. 延期、取消或无法确认的结果不会被错误计入输盘。
8. 相同数据在记录列表、比赛详情、统计页和导出文件中的结果一致；重复同步不重复计数。
9. 模拟 ROI 使用保存的赔率和一致的投入定义，观望、取消、待结算的处理可核对。
10. 历史回测与上线记录清楚分开；没有真实数据时不显示虚构成绩。
11. 输入“帮我看看今天的比赛”，先返回赛程、让分和大小分卡片，等待选择，不自动逐场深入分析。
12. 说“第 2 场”“这场只看大小分”能指向同一份列表和正确比赛；模糊指代会询问。
13. 长对话触发压缩后仍保留比赛、玩法、用户约束和未完成任务；假设不会变成事实。
14. 新聊天能召回自动保存的稳定偏好，又不会串用另一聊天正在分析的比赛。
15. 父块与子块更新一致，过期、被替代或停用的内容不再作为当前事实召回；能查看来源和维护记录。
16. 模拟数据接口超时、GPT 超时、限流及额度不足，分别进入规定状态，重试次数与总耗时均不超限。
17. 模拟浏览器断网、刷新、重复点击和主动停止，不重复创建任务、不重复写入预测；未完成内容不计为正式结果。
18. 部分数据查询失败时可保留已完成内容，明确显示缺失项；刷新盘口产生新快照，旧分析的报价不变。
19. 达到工具、模型调用、上下文或费用上限后能退出；记忆维护失败不让聊天卡死。
20. 密钥不出现在页面、聊天、记忆和普通日志中；聊天与任务、分析快照之间可相互定位。
