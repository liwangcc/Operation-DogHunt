采集时间为 2026-11-11 10:24:52 UTC，即北京时间 18:24:52。数据不是限定北京时间当天的全部赛程，而是接口当时覆盖的未来已开盘比赛。

结果目录：`data/odds/20261111T102452Z-f6416608/`。

- `snapshot.json`：完整接口事件、整理记录、来源、请求与采集时间、实际额度。
- `odds.csv`：368 条记录，适合 Excel 查看。每个平台、玩法和方向分别一行，不是 368 场比赛。

真实示例：Boston Celtics @ Toronto Raptors，FanDuel 的 Boston Celtics 盘口为 -7.5、Toronto Raptors 为 +7.5，大小分 Over/Under 均为 215.5。这只是采集时点的报价，不应在后续直接称为当前盘口或已选定参考平台。

## 为什么这样实现

新增 `scripts/fetch_nba_odds.py`，仅用 Python 标准库，避免为了先拿到数据引入网站框架和依赖。手动运行一次只请求一次，无自动循环和自动重试，不会在用户不知情时持续消耗额度。

固定请求 `basketball_nba`、`regions=us`、`markets=spreads,totals`，赔率为十进制。请求使用 `commenceTimeFrom`，返回后再按采集时间过滤已到开赛时间的比赛。原始响应仍完整保留，方便核对。开赛时间过滤不能代替完整的比赛状态核实，正式产品需另外处理改期或来源延迟。

各平台、各方向独立保存，避免按数组先后猜测主客队或把不同平台拼成一套报价。市场更新时间缺失时留空，不使用已弃用的平台更新时间冒充。当前未确定报价新鲜度阈值或唯一参考平台，不能声称所有报价都足够新或一致。

每次保存到新目录，历史采集不覆盖。`.env.local` 权限 600，用户自行填 Key；`.gitignore` 排除本地密钥与采集数据。没有读取或输出 Key 到工具日志，不在命令参数中传 Key，不在输出文件中存请求 URL；请求重定向会被拒绝，避免带 Key 的地址被转发。

新增 `.env.example` 和 `docs/API取数使用说明.md`。没有注册或购买付费套餐，没有接入 GPT、训练模型、初始化 Git，也没有改动 NBA Agent 需求文档。

## 踩过的坑与失败尝试

第一次在受限执行环境调用脚本，返回“连接失败或超时”，没有自动重试，也没有生成成功数据文件。已立即告知用户；随后通过 `require_escalated` 申请联网执行同一脚本，第二次成功。这个结果说明放宽执行环境后连接可用，但没有单独诊断 DNS、TLS 或底层网络错误，不能把具体根因当成已查明。失败请求是否曾被上游处理不能仅凭本地错误推断；最终接口显示累计已用 2、剩余 498。

## 下次从哪里继续

在项目目录执行 `python3 scripts/fetch_nba_odds.py` 可再次单次采集，每次会消耗额度。先使用已有快照查看数据，无需为展示重复调用接口。

下一步应由用户确认参考平台和更新频率，再把取数能力接入已规划的聊天 Agent。不要把 API 首次成功扩大宣称为完整赛程、历史盘口、赛果、AI 分析或网站已完成。原 Codex 联网搜索故障交接仍未解决，与本次盘口 API 成功是两条独立链路。
