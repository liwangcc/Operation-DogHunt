# NBA 聊天 Agent、记忆和异常处理需求交接

日期：2026-11-11（Asia/Shanghai）  
状态：🚧进行中；需求文档已更新到 v0.2，尚未开发或接入真实 API。

## 用户明确确认的方向

产品是以聊天为主界面的 NBA Agent，使用 OpenAI 的 GPT API 做 AI 综合分析，关注赛前全场让分与大小分。用户输入“帮我看看今天的比赛”后，先返回比赛、让分和总分数据，由用户选择场次后再分析，不能默认分析全部比赛。

需要处理同一聊天里的上下文，以及跨聊天的长期记忆。用户明确要求长期记忆自动保存、定期清理维护，并按父块与子块拆分。Agent 还必须处理超时、失败、重试和恢复。

本轮修改 `docs/NBA预测网站需求文档.md`，把产品从赛程页面为主的预测网站调整为聊天入口的 Agent 网站，版本从 v0.1 更新为 v0.2。保留原有盘口快照、赛后结算和效果验证要求。

## 为什么这样选

- 聊天中展示赛程和可选择卡片，符合用户“先列比赛，再选择”的流程，也限制不必要的深入分析调用。
- GPT 负责理解和分析，后台工具负责查真实体育数据；GPT API 不能替代盘口与伤病数据源。
- 会话状态记录选中的比赛、玩法和快照，避免“第 2 场”“这场”因列表变动指向错误对象。
- 聊天历史、当前上下文、父子块长期记忆、历史预测证据分别管理。旧盘口不能因为仍在记忆里就被当成当前行情。
- 原文保留、长对话压缩、按相关父子块召回，避免每次调用都发送全部历史。
- 父子块记忆自动保存需要来源、有效期、状态、版本和管理入口；失败时不能提示已经记住。
- 后台任务持久保存，刷新页面只恢复原任务；有限重试、统一总耗时和幂等保存，避免无限等待和重复入库。幂等是同一动作重复到达只产生一次有效业务结果，不保证上游绝无重复计费。
- 聊天中的普通追问与正式效果统计样本分开，避免每问一次就增加一笔模拟投入。

## 初始参数及未确认决策

文档建议：体育数据单次请求 10 秒、同一数据步骤含重试 25 秒、GPT 单次 90 秒、整项任务 180 秒；同一外部调用共最多两次尝试；单任务最多 6 次 GPT 请求与 12 次工具执行。连接建立计入请求时限，所有步骤都受剩余总时间限制。

这些均为待实测的产品建议值，不是用户已确认的参数，不是 OpenAI 默认配置，也不是实测性能。70% 上下文压缩阈值、每日低峰记忆维护、归档策略也只是初稿建议。

仍待讨论：具体 GPT 模型、总预算、记忆保留期限与永久删除规则、上下文由应用管理还是使用 API 对话状态能力、固定参考平台、正式预测手动标记还是定时锁定、部署方式。

已通过浏览器实际读取 OpenAI 官方文档，并在需求文档第 7.5 节放置直接链接：

本轮通用网页检索调用返回 503，已即时向用户说明并停止该路径。浏览器打开旧版 platform 地址时等待导航超时，但页面已跳转到 developers.openai.com；绑定已创建的标签后成功读取页面。页面提供的只读 WebMCP 工具随后成功返回官方正文。

一次工具调用写成了 capability 对象的 `call`，返回方法不存在；正确方式是先 `fetchTools()`，再使用返回的工具集合执行 `call`。该问题已说明并修正。资料查询故障不是本产品 GPT 调用的实测结果。

OpenAI 的长上下文压缩不等于产品可查看、可维护的长期记忆；接口状态与自有记忆需要分别设计。开发工具库的自动重试必须纳入业务总次数，避免嵌套重试。超时或取消后上游仍可能产生费用，不能承诺绝对取消或绝无重复计费。
