# 功能块设计思路

本文整理 DogRanchKiller 对 NBA 预测系统的设计思路和取舍理由。具体怎么执行，见 [功能块小批量测试方案](功能块小批量测试方案.md)。

## 1. 预测什么

- 只做 NBA 全场的**让分**和**大小分**。
- 不做亚洲盘口。最初提过，后来确认不需要。

## 2. 把影响比赛的因素拆成功能块

- 实力、节奏、赛程疲劳、伤病等影响比赛结果的因素，每个做成一个功能块。
- AI 分析或者接入 Agent 时，调用各功能块的数据和结论，再得出最终判断。不让模型一次性凭整体印象判断。
- 每块可以单独检查和改进。哪一块结论不靠谱，从记录里能直接看出来。

## 3. 每块独立提示词、单独调用模型

- 每个功能块写一份独立的提示词，Agent 按提示词输出这一块的结论。
- 每块单独调用一次模型，不把所有因素塞进同一次调用。
- 最后由汇总块合并各块结论，给出让分和大小分的判断。

## 4. 输出形式靠测试决定

- 每块都输出三样：**方向**、**把握**、**权重（分数）**。
- 原因：事先不知道“只给方向”“给方向加把握”“给权重”哪种效果更好，需要测出来，不靠猜。
- 汇总块对应做三个版本分别比较。

## 5. 小批量起步，再逐步加块

- 先做两三个块，在几场比赛上试，看结论靠不靠谱，再加其他特征。
- 每块的结果单独记录成表格（CSV），方便读取和复盘。

## 6. 程序算数字，模型下结论

- 指标计算、结算和统计由程序完成；模型只根据算好的指标做判断、说理由。
- 这样模型的结论都有具体数据可以核对，也能减少模型编造数字。

## 7. 先把数据理清

开发前先回答三个问题：

1. 数据从哪里来。
2. 拿到数据后怎么清洗。
3. 每块要不要单独存一份数据。

目前的结论：底层数据（赛程、比分、技术统计、盘口）各块共用一份；每块独立的是自己的特征计算、特征表和提示词。详见方案第 5 节。

## 8. 协作方式

- 从 `dev` 拉任务分支开发，通过 PR 合进 `dev`，之后一起把 `dev` 合并回 `main`。
